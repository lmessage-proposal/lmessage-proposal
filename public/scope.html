この提案を、どこまで確かめて書いたか

提案そのものより先に、どこまでが確認した事実で、どこからが私の判断かをはっきりさせておきます。 ここが曖昧な提案書は、受け取った側が検証に時間を使うことになり、かえって手間を増やすと考えているためです。

1. 調べ方と、情報源

提案を書く前に、次の順で確認しました。

  1. 実際に L Message に新規登録し、LINE 公式アカウントを作って接続した。 検証専用の LINE 公式アカウントを新規作成し、Messaging API を有効化して Webhook を設定し、 接続ウィザードと、その後の体験ツアーを最後まで通しました。ここで分かったことは、提案 3 を書き直す根拠になりました（後述）。
  2. L Message の公式マニュアル（lme.jp/manual）を機能ごとに読む。 配信・タグ・ステップ配信・リッチメニュー・フォーム・QR コードアクション・予約・テンプレート・料金・アップデート情報など。
  3. 「その機能はもうあるのでは」を、提案ごとに個別に確認する。 マニュアル内検索（lme.jp/manual/?s=…）で「使用中」「どこで使」「削除すると」「影響」などを検索し、 ヒットしなかったことも結果として記録しました。
  4. LINE 公式アカウント側の仕様を、LINE Developers の公式ドキュメントで裏取りする。 L Message は LINE の Messaging API の上に作られているため、 通数の数え方のようにL Message 側では決められない制約があります。そこは LINE 側の記述を根拠にしました。
  5. 第三者のブログ・まとめ記事は、根拠に使っていません。 情報が古かったり、L Message と LINE 公式アカウント本体の機能が混ざっていたりするためです。

提案の中で「✕ 見つからず」と書いた項目は、「公式マニュアル・公式 FAQ・マニュアル内検索のいずれにも記述が見つからなかった」という意味です。 「機能として存在しない」と断定したものではありません。 マニュアルに書かれていない機能が画面にある可能性は十分にあります。 社内の方が見て「それはもうある」という箇所があれば、その提案は取り下げます。

2. 書き直した箇所と、まだ確認できていないこと

実際に触って、書き直した箇所

提案 3 の課題 3-3 は、当初の内容が誤っていました。

公式マニュアルだけを読んでいた段階では、「製品内に初期設定を支援する仕組みは、LINE 公式アカウントの接続部分にしかない」 と書いていました。実際に登録して接続したところ、接続直後に 5 つのハンズオンからなる体験ツアーがあり、 体験のたびに自分の LINE へ解説が届くという、想像よりずっと手厚い作りでした。

マニュアルの記述からは読み取れない部分で、触らなければ気づけませんでした。 この発見で提案 3 は「無いものを作る」提案から 「よくできている体験ツアーの出口に、自分の店の設定への一段を足す」提案に変わり、 既存の導線に乗る形になりました。内容としては、書き直したあとの方が良くなっています。

誤りを消さずにここに残しているのは、 公開情報だけで書いた提案がどこで外れるかを、具体的に示しておく方が誠実だと考えたからです。

提案 1 も、実機で確かめて一部を書き直しました。

  • 「配信内容を確認して送信に進む」というボタン名は公式どおりで、実機でも確認。
  • 「プレビュー・テスト送信」画面に「概要」タブ（タイトル・配信日時・絞込み要約）があり、 「1 か所にまとめる」発想の芽がすでにあると分かったため、提案を「このタブを育てて送信直前に置く」形に捉え直し、第 1 段の工数の下限を 6→5 人日に修正。
  • 配信先のそばに「再計算」ボタンがあり、人数が自動更新されないと分かったため、課題に「編集時点と再計算時点のずれ」を追記。
  • エルメがURL を既定で計測用に置き換えると分かったため、リンク検査の対象を「入力時の URL」に修正。
  • プレビューは実機風ではなく簡易表示だと確認。

提案 2（タグまわり）は、タグ一覧と削除ダイアログをまだ実機で見られていないため、記述が外れている可能性が残っています。

まだ確認できていないこと

検証用アカウントは作りましたが、次の点はまだ確認できていません。

  • タグを削除するときに、画面上で何か警告が出るか。 マニュアルには記述がありませんでしたが、画面には出ているかもしれません。 タグ一覧と削除ダイアログは、今回まだ実機で確認できていません。提案 2 で最も確認したい 1 点です。
  • 各一覧画面に実際に並んでいる列。 公式マニュアルが列構成を明記しているのはリッチメニュー・QR コードアクション・フォーム・タグの 4 つだけで、 ステップ配信一覧・自動応答一覧・テンプレート一覧などは記載がありません。
  • 画面の動作の速さ。検証アカウントの友だちは 1 人、タグは 0 件なので、 数が増えたときの重さは測れません。提案 2 の工数の幅は、ここが見えないことから来ています。
  • 内部の作り。工数見積もりの幅は、最終的にここが見えないことに起因します。

この前提を踏まえて、各提案の工数は「幅」で出しています。 1 つの数字で出す方が読みやすいのは承知していますが、 見ていないものを 1 つの数字で出すと、根拠のない数字になります。 社内で実際の画面と作りを前提にもう一度見積もれば、幅はかなり詰められます。

3. 工数の数え方

1 人日の定義

L Message の開発に慣れたエンジニア 1 名が、実働 1 日（7 時間）で進められる量を 1 人日としています。

含むもの

  • 要件の整理（何を作るかを決める話し合いを含む）
  • 実装
  • 簡易テスト（自分で動かして確認する範囲）
  • レビューでの指摘対応

含まないもの

  • デザイン制作（画面デザイン・画像素材）
  • 本格的な QA・受け入れテスト
  • リリース作業と、その後の監視
  • マニュアル・ヘルプの更新
  • 法務・薬機法などの確認

実際に必要な期間は、この人日におおよそ 1.5〜2 倍を見ていただくのが安全だと考えています （レビュー待ち・他の作業との並行・仕様の確認待ちが入るため）。

幅の付け方

各項目の人日を「下限〜上限」で出しています。考え方は次のとおりです。

幅意味例
幅が小さい（例 1.0）やることが決まっていて、既存の作りに左右されにくい一覧に列を 1 つ足す
幅が 1.5 倍程度作る量は読めるが、細かい調整が読みきれない自動チェック 9 項目（2.0〜2.5 人日）
幅が 1.5 倍を超える既存の作りを見ないと判断できない部分がある参照関係を集める仕組み（4.0〜6.0 人日）

幅が大きい項目は、見積もりの精度が低いことを隠さずに示している箇所です。 提案 2 の「参照関係を集める仕組み」がこれにあたります。 実務では、ここに先に 1 日だけ調査の時間をもらう（調査のための工数を見積もりに入れる）のが現実的だと考えています。

4. ご依頼者の立場で、入れておいた方がよいと判断したこと

提案の良し悪しとは別に、実際に作ると決めたあとで必ず問題になることを、先に書いておきます。 提案書に書いていないと、あとから「聞いていない」になる種類の項目です。

4-1. 「良くなったか」を何で測るか

3 件とも、導入前に測り方を決めておかないと、効果が分からないまま終わります。 各提案の確認事項にも書きましたが、まとめるとこうなります。

提案測りたいこと測れないときの代わり
提案 1送信取り消しの実行回数、誤配信に関する問い合わせ件数確認画面で「戻る」を押した回数（＝事故を未然に止めた回数の近似）
提案 2タグ・設定の削除件数、アカウントあたりの設定数の推移「使用箇所」表示を開いた回数
提案 3登録から 30 日後も配信しているアカウントの割合ひな形を適用したアカウントの、7 日以内の初回配信率

4-2. 出す順番と、引き返せるようにしておくこと

  • 3 件とも「表示を足す」方向で、既存の設定を書き換えません。 これは意図的です。設定を書き換える機能は、問題が起きたときに元に戻せません。
  • 提案 1 の第 2 段「予約配信のずれを検知して保留する」だけが、唯一配信そのものに手を入れる箇所です。 ここは既定でオフにし、希望するアカウントだけが有効にできる形を提案しています。
  • いずれも一部のアカウントに先に出して様子を見ることができる内容です。全アカウントに一斉に出す必要はありません。

4-3. 開発以外にかかるコスト

工数見積もりに含めていない、しかし確実に発生するものです。

  • マニュアルの更新。L Message の公式マニュアルは機能ごとに丁寧に書かれています。 画面が変われば、該当ページの文章と画像を差し替える必要があります。提案 1 なら配信関連の数ページが対象です。
  • サポート窓口への説明。「配信前に新しい画面が出るようになった」ことを知らないと、問い合わせに答えられません。
  • 代理店・認定講座の教材。御社は認定講座（導入支援コース・代理店コース）をお持ちなので、 画面が変われば教材も影響を受けます。
  • 提案 3 のみ、公開後もずっと続くコストがあります（業種別の中身の更新）。これが提案 3 を 3 番目にした理由の 1 つです。

4-4. やらない方がよい、と判断する基準

提案した側が言うことではないかもしれませんが、作らない方がよい条件も書いておきます。

  • 提案 1: 誤配信に関する問い合わせがほとんど届いていないなら、優先度を下げるべきです。 ただしこの場合も、「問い合わせが来ていない」のか「諦められている」のかは区別が必要だと考えます。
  • 提案 2: タグが 100 個を超えるアカウントが全体のごく一部なら、作る価値は小さくなります。
  • 提案 3: 登録後に配信ゼロで離脱する割合が小さいなら、作るべきではありません。 また、制作代行・認定講座の事業と競合しうる場合は、技術の話より先に事業の判断が必要です。

5. 調べる途中で気づいた点

提案には入れていませんが、お伝えしておいた方がよいと判断したものです。

公式マニュアル内に、数字が食い違っている箇所があります

1. 吹き出しと通数の関係

  • 「配信数カウントの仕組み」のページ: 5 吹き出しで LINE 公式アカウント配信数が 1 カウント
  • 「目的から探す・よくあるご質問」のページ: LINE 公式アカウントは3 つの吹き出しで 1 通とカウント

LINE Developers の公式ドキュメントを確認したところ、Messaging API の仕様はこうでした。

1 回のリクエストに含められるメッセージオブジェクトは最大 5 つ。 送信したとカウントされる通数は送信した人数であり、 1 回のリクエストに含めたメッセージオブジェクトの数は、通数に影響しない。

つまり 「5 吹き出しまでが 1 通、宛先の人数分だけ通数が増える」のが LINE 側の仕様です。 マニュアルの「3 つの吹き出しで 1 通」という記述は、現在の仕様と合っていない可能性があります。 通数は料金に直結するため、ここは直す価値があると思います。

2. 配信数のリセット日

  • 「配信数カウントの仕組み」のページ: リセット日はエルメ・LINE 公式アカウント共に毎月 1 日
  • 「目的から探す・よくあるご質問」のページ: 無料プランは接続した日を基準に 1 か月ごと、有料プランは契約日を基準に 1 か月ごと

こちらは実機で判断材料が見つかりました。 管理画面の「配信数サマリー」には 「配信数のリセット日はエルメ・LINE 公式アカウント共に毎月 1 日です」と注記されています。 製品は「毎月 1 日」で動いているようですので、 「目的から探す・よくあるご質問」側の記述が古いのではないかと考えています。

どちらも利用者の料金に関わる記述です。どちらが正しいかは社内でないと判断できないため、提案には含めず、ここに記載しました。

6. 用語の説明

この提案で使っている、説明なしでは伝わりにくい言葉です。

言葉意味
人日（にんにち）エンジニア 1 人が 1 日働いて進む量。「5 人日」は、1 人なら 5 日、2 人なら約 2.5 日かかる量。ただし人を増やせば比例して早くなるとは限りません。
Push メッセージ / Reply メッセージLINE 側の区分。こちらから送るのが Push（料金のカウント対象）、友だちの操作に応じて自動で返すのが Reply（カウント対象外）。あいさつメッセージや自動応答は Reply、一斉配信やステップ配信は Push です。
吹き出しLINE のトーク画面に出る、1 つの発言の枠。1 回の配信で複数の吹き出しをまとめて送れます。
逆引き「A が B を使っている」という関係を、B の側から「誰が自分を使っているか」と調べること。提案 2 の中心です。
fail closed（フェイルクローズド）設定が足りないときに「通す」のではなく「止める」側に倒す考え方。このサイトの Basic 認証もこの作りにしています（下記）。
noindex検索エンジンに「この内容を検索結果に出さないでください」と伝える指定。
Basic 認証ページを開くときにユーザー名とパスワードを求める、最も基本的な仕組み。
段階導入全部を一度に作らず、効果の大きい部分から順に出すこと。途中でやめる判断ができるのが利点です。

7. このサイト自体の作り

項目内容選んだ理由
公開環境 Vercel 課題で指定された選択肢の 1 つであり、Basic 認証を全ページにかけるための仕組み（Routing Middleware）が標準で使えるため。
言語・構成 静的な HTML / CSS と、認証用の JavaScript 1 ファイル 読む資料のサイトに、フレームワークは不要と判断しました。ビルドが要らず、外部フォント・外部 JS・外部 CSS を一切読み込まないため、表示が速く、将来も壊れにくくなります。
図 すべて手書きのインライン SVG 画像ファイルではないため拡大しても粗くならず、画面の明暗（ライト／ダークモード）にも追従します。読み上げ用の説明文も図ごとに付けています。
検索避け 各ページの meta robots と、全パスへの X-Robots-Tag ヘッダーの二重。加えて robots.txt 課題の指定どおり。片方だけだと、HTML を読まない取得（画像・CSS など）に効かないため両方かけています。
Basic 認証 Vercel の Routing Middleware で全パスに適用 対象パスを絞る設定をあえて書いていないため、HTML だけでなく CSS や robots.txt も認証なしでは取得できません。
パスワードの置き場所 ソースコードに書かず、Vercel の環境変数から読む。未設定なら全リクエストを拒否 ソースに書くと、リポジトリを見られた時点で意味がなくなります。また「設定を忘れたら誰でも見られる」ではなく「設定を忘れたら誰も見られない」側に倒しています。
外部素材 使用なし（OS のフォントのみ） 第三者素材のライセンス確認が不要になり、提出物として扱いやすくなるため。
